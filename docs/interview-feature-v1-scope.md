# 面试总结（音频转文字 → 分析报告）· 需求方案 v1.0（需求已冻结）

> 本期**只做一个功能点**，一条直线流程，不含向量化、不含模拟面试。
> 历史版本已作废，以本文为准。
>
> **2026-10 修订（v1.1）**：报告由"三部分"改为"三部分 + 完整对话附录"。理由：只给问答清单时，
> 没被识别成问答的对话（岗位介绍、流程说明、改约协调）在报告里**完全不可见**，
> 用户会以为系统漏读了录音；实测一段 5.5 分钟录音里 71 句只有 2 句是提问，
> 报告因此显得"只有一条对话"。受影响处：§2 的板块表与"不要的板块"、§6 验收、§8 后端接口。
> 实施细节见 `docs/interview-step4-report.md` §9。

---

## 1. 主流程

```
用户上传面试音频 → 音频转文字稿 → 总结面试 → 输出面试总结文档
```

用户操作只有两步：**上传音频** → **查看/下载总结文档**。中间过程系统自动完成。

---

## 2. 输出文档必须包含（本期核心）

报告**只包含以下四部分**，不做其他板块：

| # | 板块 | 内容要求 |
|---|---|---|
| 1 | **问答清单** | 整场面试官问的**每一个问题** + 用户当时的回答。回答 = **忠实摘要 + 摘出关键原话**（不整段照搬）。时间戳保留在结构化数据里，正文不展示（v1.1） |
| 2 | **知识点清单** | 这场面试涉及到的知识点，按主题归类，标注每项出现在哪个问题上 |
| 3 | **待补充知识点** | 用户回答不到位 / 没答上来 / 只停留在表面 的知识点，说明**为什么需要补**、**补什么方向**。**不标优先级** |
| 4 | **完整对话**（v1.1 新增） | 整场对话**逐句原文**（说话人 + 时间戳 + 原话，**不改写、不摘要、不省略**），附在报告最后 |

已明确**不要**的板块：本场概览、总评、评分。

> **为什么第 4 部分不是"本场概览"**：本场概览是模型对整场的**概括**（禁止，会引入主观判断）；
> 第 4 部分是**逐字原文**，作用只有一个 —— 让用户核对"问答清单有没有漏"。
> 一段面试里大量内容不是问答（岗位介绍、流程说明、改约），
> 只给问答清单会让这些内容在报告里彻底消失。

### 报告长什么样（格式约定）

- 内容以 **Markdown** 组织，直接可读
- 存储为**文件放进 MinIO**，数据库只存元信息 + 访问地址（见 §5）
- 前端页面渲染展示，同时给出**下载地址**供用户下载原文件

## 3. 范围边界

### ✅ 本期做
- 上传**音频文件**（mp3 / wav / m4a / aac / flac / amr / wav），**单文件 ≤ 80MB、时长 ≤ 1.5 小时**；超出直接报错提示，不做分段
- 音频转文字（**必须能区分面试官和用户**，否则第 1 项做不出来）
- 生成上述三部分的分析报告，**报告文件存 MinIO**，页面查看 + 提供下载地址
- 保留原始文字稿（用户能核对报告是否准确，这是可信度的关键）

| 不做 | 原因 |

| **模拟面试** | 后续再做 |
| 打分 / 评分体系 / 总评 | 本期只陈述"问了什么、答了什么、缺什么" |

| 待补充项优先级排序 | 已确认不要 |

| 实时语音面试 | 后续 |

## 4. 关键技术选型

| 环节 | 选型 | 说明 |
|---|---|---|
| **音频转文字** | **阿里云百炼 `qwen-audio-3.1-asr-flash-filetrans`**（异步 HTTP API） | 与项目现有百炼 Key/域名同源，同一把 Key 就能用；单文件支持 **12 小时 / 2GB**；**支持说话人分离**（这是本期能否区分"谁问谁答"的前提）；支持热词、标点、时间戳 |
| **音频送达** | **开发环境**：百炼临时文件上传换 `oss://` URL<br>**生产环境**：MinIO 暴露公网 URL 直接喂百炼 | 百炼**不接受字节流/Base64**，只接受公网 URL（详见 §4.1） |
| **音频预处理（可选）** | 转成 16k 单声道后再送转写 | 说话人分离**只对单声道有效**；双声道文件需先合并 |
| **区分面试官/用户** | ASR 输出 `speaker_id` → 用 LLM 按对话模式判定角色 | ASR 只告诉"这是第几个人"，不告诉"谁是面试官"；由总结阶段一并推断 |
| **总结生成** | 复用现有 `ChatModel`（qwen3.8） | 长音频**分段抽取问题 → 汇总生成报告**，避免超上下文（现有 `maxTokens: 10000`） |
| **报告格式** | 模型产出**结构化 JSON** → 后端渲染成 **Markdown 文件** → **存 MinIO** → 数据库存元信息与访问地址 | JSON 中间态保证解析可靠、为后续向量化/模拟面试留结构；Markdown 文件便于用户直接下载 |
| **报告下载** | MinIO 提供下载 URL（生产走公网域名，开发走内网地址） | 与音频同一套存储能力，不新增组件 |
| **异步任务** | Spring `@Async` + 任务状态落库 | 项目当前**没有**异步能力，转写要几分钟，必须异步 |
| **存储** | 复用现有 MinIO + MySQL | 不引入新组件 |

**明确不采用**：
- ❌ **MCP** 做音频转写（分钟级长任务 + 大文件，与 MCP 的工具调用模型不匹配）
- ❌ **Spring AI 的 `AudioTranscriptionModel`**（只覆盖 Whisper 语义，无说话人分离、无异步长音频）

### 4.1 音频怎么"送给"百炼（这里容易误解，单独说明）

**先纠正一个常见预期**：这个转写接口**不是**把音频字节流传给模型。阿里云百炼的录音文件识别是**异步任务式**接口，官方明确规定：
> 不支持 Base64 编码方式的音频，仅支持可通过公网访问的 URL 所指向的音频，不支持识别二进制流，也不支持直接识别本地文件。

所以链路必然是「**先让音频有个 URL，再把 URL 交给百炼**」，百炼自己去下载音频。区别只在于"这个 URL 从哪来"。**本期按环境分两套实现**：

#### 开发环境：百炼临时文件上传

```
音频 → 存 MinIO（自己存档，用于 30 天保留 / 失败重试）
     → 调百炼「获取上传凭证」接口
     → 把音频 POST 到百炼给的 upload_host
     → 百炼返回 oss://dashscope-instant/... 临时 URL（有效期 48 小时）
     → 提交转写任务时带上这个 URL + 请求头 X-DashScope-OssResourceResolve: enable
     → 百炼读取并转写
```

**优点**：本地开发**完全不需要公网域名**，不需要改网络配置就能跑通全流程。

**限制**（官方标注）：临时 URL 有效期 48 小时；上传凭证接口 100 QPS 且不可扩容。开发环境无所谓。

#### 生产环境：MinIO 暴露公网 URL

```
音频 → 存 MinIO → 取 MinIO 公网访问 URL → 直接交给百炼
```

省掉一次中转上传，链路更短、更稳，不受百炼临时存储的 QPS 与 48 小时限制。

**前置条件**：生产环境 MinIO 必须配置**公网可达域名**（或反向代理 / 换阿里云 OSS）。这是上线前必须落实的运维项。

#### 两套怎么切

把"**取音频 URL**"抽成一个接口（如 `AudioUrlProvider`），按配置/Profile 注入两种实现：

| 环境 | 实现 | 需要的配置 |
|---|---|---|
| dev | `DashScopeTempUrlProvider`（临时上传） | 仅需百炼 API Key |
| prod | `MinioPublicUrlProvider`（公网 URL） | `minio.public-base-url`（对外域名） |

**切换只改配置，不改业务代码。**

#### 无论哪套，音频都要存 MinIO

原因有二：转写失败要能**原地重试**，不能让用户重新上传；原始音频需要**保留 30 天**（百炼临时 URL 48 小时就失效，结果链接也是 24 小时失效，都要靠自己落库/落盘）。

## 5. 数据流与耗时预期

```
上传音频
  → MinIO 存储原始音频（1~3 秒，接口立即返回）
  → 校验：格式 / ≤80MB / ≤1.5 小时（不达标直接报错）
  → 取音频 URL（dev=百炼临时上传；prod=MinIO 公网 URL）
  → 提交百炼转写任务（异步）
  → 轮询等待（40 分钟音频约 1~4 分钟）
  → 下载识别结果 JSON（链接 24 小时失效，必须立刻落库）
  → 归一化为文字稿（说话人 + 时间戳）落库
  → 分段抽取问题清单（每段一次 LLM 调用）
  → 汇总生成报告三部分
  → 渲染成 Markdown 文件 → 存 MinIO → 落库报告元信息与访问地址
  → 前端展示报告 + 提供下载地址
```

**耗时预期**：40 分钟音频，端到端 **3~8 分钟**。页面显示阶段化进度（转写中 → 分析中 → 完成）。

## 6. 效果验收标准

| # | 验收项 | 标准 |
|---|---|---|
| AC-1 | 上传响应 | 大文件上传完成后 **3 秒内**返回任务 ID，页面进入处理中状态 |
| AC-2 | 说话人区分 | 文字稿能区分出两个说话人，且**面试官/用户角色判定正确**（Complete 对话里逐句标注角色） |
| AC-3 | 问题提取完整性 | 人工核对：报告中遗漏的问题 **≤ 2 个**（相对实际提问数） |
| AC-4 | 问答对应准确 | 每个问题能对应到正确的回答，不串位 |
| AC-5 | 知识点覆盖 | 报告中的知识点确实在音频中出现过，**不编造**（抽查 10 条，错误 0 条） |
| AC-6 | 待补充项的合理性 | 待补充知识点确实对应"回答不到位"的地方，不能把答得好的也列进去 |
| AC-7 | 端到端耗时 | 40 分钟音频 ≤ 8 分钟出报告 |
| AC-8 | 失败可恢复 | 转写或分析失败时，状态明确、可重试，不用重新上传音频 |
| AC-9 | 超限拦截 | 超过 80MB 或 1.5 小时的音频，明确报错并提示原因，不产生脏任务 |
| AC-10 | 报告可下载 | 报告页提供下载地址，点击可下载 Markdown 原文件 |
| AC-11 | 开发环境可跑通 | 本地开发无需任何公网域名配置，端到端流程可完整跑通 |
| AC-12 | **完整对话可核对**（v1.1） | 报告最后包含**逐句、未改写**的完整对话；报告里出现的话语必须能在该附录中逐字找到（即"报告没有凭空产生内容、也没有把没抽到的内容藏起来"） |
| AC-13 | **同一音频结果稳定**（v1.1） | 同一个 `interviewId` 连续重新生成 ≥3 次，问答对数量与待补充知识点条数**一致**（不允许因采样随机而每次不同） |

## 7. 为后续功能预留（本期不做，但结构留好）

你说后续会做登录、用户天然隔离。本期不做登录，但：

| 预留项 | 本期做法 |
|---|---|
| 所有新表带 `user_id` 字段 | 本期写入固定占位值 |
| Service 方法带 `userId` 参数 | 本期传占位值 |
| 报告**同时保留结构化 JSON**（除了 MinIO 里的 Markdown 文件） | 后续向量化、模拟面试可直接复用，不用反过来解析 Markdown |
| 文字稿按**句子 + 时间戳 + 说话人**结构化保存 | 后续可直接按问答轮次切分向量化 |

> 说明：报告存 MinIO 是为了给用户一个**可下载的文件**；但结构化 JSON 仍要落库，否则后续做向量化和模拟面试时得去解析 Markdown，成本高且易错。两份数据来源相同，不冲突。

## 9. 风险与不确定项（需你知晓）

| 风险 | 说明 | 应对 |
|---|---|---|
| **录音质量决定说话人区分效果** | 若面试时用户戴耳机、面试官声音从外放传出，两人音质差异大，可能分不清谁问谁答 | 开工前**先拿一段真实录音验证**；若不达标，改用双声道分轨录音（天然区分） |
| 长音频超上下文 | 60 分钟面试文字稿约 1.5~2.5 万字，接近模型上限 | 采用分段处理，已在方案中体现 |
| 转写专业术语出错 | 技术名词易识别错 | 用百炼**热词**功能，把岗位相关技术名词传进去提升准确率 |
| 成本 | 转写按语音内容时长计费，分析按 Token 计费 | 单场量级很小（毛级），但建议加成本记录便于观察 |
| 合规 | 面试录音属敏感个人信息 | 上传页需勾选"已获得录音各方同意"；提供彻底删除（含原始音频） |
