# 步骤 3 实施记录：说话人角色判定 + 问答对抽取

> 对应编码方案 §4 步骤 3。输入是步骤 2 落库的 `ai_interview.transcript_json`。
> 测试音频：`interView.m4a`（5 分 31 秒，72 句，2 个说话人）。
>
> **2026-10 修订**：有人提出"能否干脆不判角色、直接按模型给的问答输出"以省 token、提速。
> 结论是**保持现状（独立角色判定 + 块内标签）**，理由与实测数据见 §8。本文其余部分为改造前原文。

## 1. 最终达到的效果

把"一堆带 `speaker_id` 的句子"变成"谁问的、谁答的"结构化问答：

```
输入：72 句文字稿（speaker_id ∈ {0,1}，但编号本身没有身份含义）
  ↓ ① 角色判定（LLM ×1，输入采样片段）
面试官 = Speaker1，候选人 = Speaker0   → 落库 interviewer_speaker_id
  ↓ ② 问答抽取（LLM ×N，按对话轮次分块）
Q001 [00:57] 这是在学校还是在家的？ → 候选人表示现在在学校，在教室里。
Q002 [01:28] 你明年毕业之后还会考研吗？ → 候选人表示没有考研、考公的打算。
```

**时间戳不是模型给的**：模型只输出句子序号，时间由序号在真实句子数据里查到后回填
（实测 Q001 的 `questionBeginMs=57530` 与文字稿第 7 句的 `beginMs=57530` **完全相等，误差 0ms**）。

## 4. 关键设计决策

| 决策 | 理由 |
|---|---|
| **角色判定用 LLM，不用规则** | ① 百炼的 `speaker_id` 是声学聚类编号，**跨任务没有稳定含义**，无法用规则映射；② 也不能只看说话时长 —— 面试官可能长篇介绍公司/团队（步骤 0 的录音正是如此） |
| **只采样开头 + 中段 + 尾段各 25 句** | 判定只需要少量代表性对话；整篇送进去浪费 token 且可能超上下文 |
| **LLM 只输出句子序号，输出后校验** | 不采信模型给的时间数字；序号必须存在于文字稿，否则**丢弃该条**而不是写入错误时间戳 |
| **按对话轮次分块** | 以面试官每句话为起点切轮次，每块约 `max-questions-per-chunk`（默认 8）轮。按轮次切而非按句数切，避免把一问一答劈到两个块里 |
| **单块失败隔离** | 某块抛异常（含输出被截断）只记入 `failedChunks` 并继续，不让整场面试失败 —— 这是步骤 3 的验收项 |
| **跨块去重** | 相邻块可能重复抽出同一个问题，用"问题文本 + 起始时间"去重后再全局编号（Q001、Q002…） |
| **截断检测（方案 1）** | 解析前先看 `finishReason`，为 `length` 直接抛 `LlmOutputTruncatedException`，而不是把半截 JSON 丢给 Jackson 换一个没有信息量的解析异常 |
| **不自己剥 think 标签** | 读 Spring AI 1.1 字节码确认：`BeanOutputConverter` 默认挂了 `WhitespaceCleaner → ThinkingTagCleaner → MarkdownCodeBlockCleaner → WhitespaceCleaner`，已自动处理 `<think>/<thinking>/<reasoning>` 与 ``` 围栏 |
| **`@Async` 靠事件触发** | 轮询方法与监听方在同一个 Bean 里，同类直调会绕过代理静默变同步；用 `ApplicationEventPublisher` 派发，监听方是容器里的代理对象，`@Async` 才生效 |

## 8. 2026-10 复核：角色判定要不要去掉

> 触发问题：**"步骤 3 既然要判角色，那干脆不判，直接让模型输出问答，文档里也不标面试官/候选人，
> 用户看语义就知道谁在问 —— 这样不是更省 token、响应更快吗？"**
>
> 结论：**不采用**，保持现有"独立角色判定 + 分块时告知角色"的做法。

### 8.1 先把"省 token"这件事算清楚

按 40 分钟音频（约 **520 句**、`max-questions-per-chunk=8` 轮）估算，分块后约 **65 块**，
每块输入 ≈ 3,000 token（系统规则 + 角色说明 + 约 50 句正文），全流程输入约 **175k token**：

| 开销项 | 量级 | 占全流程输入 | 说明 |
|---|---|---|---|
| 那次独立的角色判定调用 | 约 **5k token**、约 **6 秒** | **≈ 3%** | 采样 3×25 句，只输出一个编号 + 一句依据 |
| 每块每行的 `[Speaker1]` 标签 | 约 **6.5k token** | **≈ 4%** | 全流程约 4,000 行 × 约 1.5 token |
| 输出的问答摘要 / 原话 / 知识点 / 报告 | 与输入同量级或更多 | **大头** | 去角色完全不影响这一项 |

**合计只省 2%~5% 的 token**，端到端（2~8 分钟）快不到 2%。
拿这个收益去换下面的风险，不划算。

> 口径说明：这里的句子数、分块数与 token 数是**按实测比例外推的估算**，
> 不是逐条统计出来的 —— 依据是手上这段 5.5 分钟音频实测为 72 句 / 6 块 /
> 2 分 20 秒（§5.2、§5.3），按 40 分钟等比放大。真实技术面试录音到位后应复核一次。

### 8.2 真正的代价不是 token，是三件事

| 风险 | 具体表现 |
|---|---|
| **分块方式要退化** | `InterviewQaExtractor.buildTurns()` 是"以面试官的句子开新轮"，`partition()` 按轮分组。角色消失后只能按句数切，**一问一答被劈到两个块的几率明显上升** —— 这正是当初选"按轮切"要避免的问题 |
| **65 个块各自判角色，错误会相乘** | 现在是一处判断管全场（错了是一次错误）；去掉后每个块都要自己猜"谁在问"，40 分钟里几十处提问/转述边界，只要有块理解反，问答就串位，且**没有任何机制能发现** |
| **候选人的反问会被当成一条 Q** | "这个岗位具体做什么？""团队多少人？"这类候选人反问，很容易被抽成面试官提问，需求 AC-3 / AC-4 直接不合格 |

另外，需求文档 `interview-feature-v1-scope.md` §6 的 **AC-2 明确要求"面试官/用户角色判定正确"**，
§4 技术选型表也写着"ASR 输出 `speaker_id` → 用 LLM 按对话模式判定角色"。
去掉角色判定等于同时改技术方案与验收标准，而不是一次实现优化。

### 8.3 保留下来的额外价值

现在每块 prompt 都带着"面试官 = SpeakerX，候选人 = SpeakerY"这一句（**约 50 token/块**，
全流程约 3k token）。它买到的是一条**免费的交叉校验**：

- 模型在每个块里被反复告知角色，块内问答归属不会漂移；
- 由于所有块用的是**同一个**角色结论，跨块也不会自相矛盾；
- 与那次"采样判角色"的调用一起，构成"一次判定 + N 次复用"的结构 ——
  比"不判 + N 次独立猜测"稳健得多。

### 8.4 保持现状，但记下一个可选加强项（本次未实施）

现在的 `QA_EXTRACTION_SYSTEM` 里**没有**"提问与回答必须来自不同说话人"这条约束。
它是防串位最直接的一条规则，加进去成本极低（一行 prompt）：

```text
8. 一个问答对里的提问者与回答者必须是不同的说话人；若同一说话人自问自答，不要抽取。
```

本次**不改**，原因有二：① 现有 prompt 已稳定通过 5.5 分钟音频的抽取（未串位）；
② 改 prompt 会让 §5.2 的实测结果失去对应关系，需要重跑一遍才能回写。
留作真实技术面试录音回归时的候选改动。

### 8.5 与步骤 4 改造的关系

同一轮讨论还改了**问答清单的展示**（正文去时间戳、压成 Q/A 两行），
那是纯渲染层改动，**与本节的结论互不影响**：角色判定照旧跑、`interviewer_speaker_id` 照旧落库、
`report_json` 结构照旧不变。详见 `docs/interview-step4-report.md` §8。

## 9. 2026-10 回归：这段音频暴露的两个真问题（已修）

> 起因：用户拿同一段 `interView.m4a` 重跑，报告里**只剩 1 条问答对**，
> 而步骤 3 当初实测是 2 条。查下去发现是两个独立问题。

### 9.1 先澄清一个误解：71 句里只有 2 句是提问

把这条记录的完整文字稿拉出来逐句看过（当时用的 `GET /interview/{id}/transcript`，71 句；
该接口已在 v1.8 移除，文字稿现在随报告的第四部分「完整对话」返回）：

| 句 | 说话人 | 内容 | 性质 |
|---|---|---|---|
| 7 | 面试官 | 这是在学校还是在家的？ | ✅ 真提问 1 |
| 12 | 面试官 | 所以我了解一下你明年毕业之后还会考研吗？ | ✅ 真提问 2 |
| 10–11 | 面试官 | 介绍岗位 / 团队 / 转正 | 岗位介绍，prompt 明确排除 |
| 19–31 | 面试官 | 讲面试流程、自我介绍、要求 coding | 流程说明，排除 |
| 32–52 | 双方 | 候选人没带电脑 → 改约、问时间 | 改约协调，排除 |
| 53–71 | 双方 | 约明天下午 2 点、告别 | 寒暄，排除 |

**上限就是 2 条问答对**，产出 1 条说明模型漏了一条，而不是管道丢了数据。
这也说明原文档里"抽出问答对数量与实际提问数量偏差 ≤ 2"这条验收在这段音频上几乎没有判别力
（基数 2，漏 1 个就是 50%）。

复刻 `InterviewQaExtractor` 的分块逻辑后得到：

```
轮次数=44   分块数=6（chunkSize=8）
chunk1 句子 1-10   ← 提问在句 7
chunk2 句子 11-22  ← 提问在句 12
chunk3 句子 23-33  ← 0 个提问（流程说明）
chunk4 句子 34-49  ← 0 个提问（coding 约定）
chunk5 句子 50-64  ← 0 个提问（改约时间）
chunk6 句子 65-71  ← 0 个提问（告别）
```

**6 次 LLM 调用里有 4 次面对的是一整块没有任何提问的独白。**

### 9.2 问题一：同一音频连跑 5 次，结果在变

对同一个 `interviewId` 连续跑 5 次 `POST /analyze`（不重新转写、不重复计费；
v1.8 起等价于 `POST /interview/{id}/retry`）：

| 运行 | 问答对 | 知识点主题 | 待补充 | 抽到什么 |
|---|---|---|---|---|
| 用户那次 | **1** | 0 | 0 | 只有"考研吗" |
| 复现 1~4 次 | 2 | 0 | 0 | 句 7 + 句 12 |

**根因**：`application.yml` 里 `spring.ai.openai.chat.options.temperature: 0.7` 是全局默认
（给对话/PPT 写的），而问答抽取与知识点归纳都是**信息抽取**任务 —— 采样发散意味着
同一份输入不同时间跑出不同报告，直接违反 AC-13。

**修法**：`LlmJsonSupport` 增加"按次传温度"的重载，抽取链路统一走
`EXTRACTION_TEMPERATURE = 0.1`；用 `Prompt(messages, options)` 只覆盖温度，
**不动 yml 里的全局 0.7**，所以对话与 PPT 的行为完全不变。
（不用 0.0 而用 0.1：0.1 实测已一致，同时避开部分服务端对 `temperature=0` 的边界差异。）

### 9.3 问题二：模型把"回答范围"写窄

句 12 的回答其实是句 13–17 连续五句，但抽出来的 `answerBeginSeqNo/answerEndSeqNo`
只覆盖句 17，于是：

- `answerSummary` 只反映了最后半句；
- `answerQuotes` 只摘到"就是就业打算，就没有考研考公的打算。"，丢了"我没有就业的打算"。

时间戳不受影响（回填仍取真实毫秒），但摘要与原话偏薄。

**修法**：`QA_EXTRACTION_SYSTEM` 第 5 条补一段约束（回答范围必须覆盖候选人连续的多句），
第 1 条补一句"面试官只要真的在提问就必须抽出来，包括简短的确认式提问"。

### 9.4 顺带优化：跳过没有提问的分块

新增 `hasQuestionCandidate(chunk, interviewerSpeakerId)`，在调用 LLM **之前**判断该块里
面试官是否有"提问候选句"：

- 命中信号只有两类：**问号**（中英文），或**疑问/引导词**（什么 / 怎么 / 哪 / 是否 / 吗 / 介绍 / 说说 …）；
- 判定刻意**宽松**（宁可多调一次也不漏问题），并且**只看面试官的句子** ——
  候选人的反问（"那我怎么办呢？"）不是问答对里的"问"，抽出来只会污染报告。

跳过与失败**分开记**：新增 `AnalysisResult.skippedChunks`，与 `failedChunks` 并列。
报告里跳过只写一句"已跳过 N 个不含提问的片段"，而失败才标"问答清单可能不完整" ——
跳过是正常优化，不该让用户以为内容缺失。

实测效果：这段音频的分块从"6 次调用"降到"2 次调用"，**省 2/3 的 LLM 调用与等待时间**。

### 9.5 仍需真实录音验收的部分

上面两个修复都是用**同一段无技术问答的录音**定位的，只能证明"稳定性"和"不漏调用"。
**抽取召回率与知识点质量仍然没有被验证**，还是需要一段真实的 30~40 分钟技术面试录音。

### 9.6 20 分钟音频回归暴露的第三个问题：状态查询在重复解析大 JSON

> 现象：上传一段 20 分钟音频（259 句 / 1193 秒）后，控制台每 3~5 秒稳定刷一行
> `TranscriptNormalizer : 转写稿归一化完成: 句子数=259, 说话人数=2, ...`，
> 看起来像任务卡在归一化里出不来了。

**真相**：这不是任务卡住，是 `GET /interview/{id}/status` 在**每次请求时重新解析整份
`transcript_json`** —— 它只为拿"句子数 / 说话人数"两个数字：

```java
// 旧实现（InterviewService.status）
NormalizedTranscript transcript = tryNormalize(record);   // ← 全量反序列化 80KB JSON
... transcript.speakerIds().size(), transcript.size() ...
```

于是：

| 项 | 旧行为 |
|---|---|
| 每次状态查询的代价 | 反序列化整份 ASR JSON（其中约 80% 是用不到的逐字 `words[]`）+ 构造 259 个 DTO |
| 每次还打一条 INFO 日志 | 前端轮询期间每 3~5 秒一行 → 日志被刷满，**看起来像卡死** |
| 前端为什么会轮询 | 后端的 SSE 进度流端点还没实现，前端自动降级为每 4~12 秒查一次状态 |

**这不是分析慢，是"报告进度"这件事本身在做无用功。**

**修法**（三处，都很小）：

1. 转写落库时把这两个数字写进新列 `sentence_count` / `speaker_count`
   （转写完成那一刻本来就知道，不需要以后反复算）；
2. `status()` 改为直接读列，**彻底不再触碰 JSON**；
3. `TranscriptNormalizer.normalize()` 的日志降为 DEBUG ——
   它现在只在"真正需要文字稿"的路径上被调用（转写落库、进入分析、取文字稿），
   不再是被轮询反复触发的热点。

补丁 SQL：`dobao-backend/sql/interview_step5_transcript_meta_patch.sql`
（**必须执行**，否则状态接口会因缺列报 SQL 错）。同时把前端兜底轮询从 3~10 秒放宽到 4~12 秒。

### 9.7 20 分钟音频的耗时预期

顺带给出量级，避免再把"正常耗时"当成卡死：

| 阶段 | 量级 | 依据 |
|---|---|---|
| 20 分钟音频转写 | 约 2~6 分钟 | 百炼异步任务；由 `@Scheduled` 每 5 秒轮询一次状态 |
| 角色判定 | 约 6 秒 | 一次调用，采样 3×25 句 |
| 问答抽取 | 每块约 10~30 秒 | 259 句 → 约 17 块（`max-questions-per-chunk=8`）。跳过无提问块后实际调用数会少很多 |
| 报告生成 | 约 10~30 秒 | 一次调用 |
| **端到端** | **3~8 分钟** | 与需求文档 AC-7 的上限一致 |

也就是说 20 分钟音频跑 3~8 分钟是**设计内的**。真正该被修的是"进度反馈"这条链路
（状态查询别再解析 JSON、SSE 端点补上），而不是去压缩 LLM 调用本身。

### 9.8 但"分析报告耗时很长"的根因不止于此：单次调用 220 秒

> 用户反馈：转写正常、库里能看到文字稿，**卡在"分析报告"很久**。

这次不再靠推测，直接**打点量了真实模型**（一次性探针，用与生产完全相同的
prompt 与 `BeanOutputConverter`，只调一次）：

```
[prompt]  segmentChars=2016  systemChars=762  userChars=3449  合计字符=4211
[schema]  BeanOutputConverter.getFormat() = 1331 字符
[call]    temperature=0.1  耗时=220259ms  finishReason=STOP  输出字符=2224
[call]    usage = promptTokens=2032, completionTokens=8064, totalTokens=10096
```

**一次分块抽取 = 220 秒（3 分 40 秒）。**

关键读数不是那 220 秒，而是 **completionTokens=8064 对 输出 2224 字符**：
模型真正要的 JSON 只有 2 千多字符（约 1000 token），**剩下 7000 token 全是模型"思考"**。
`finishReason=STOP` 说明它不是被 `maxTokens` 截断，而是自己想了这么久。

于是这道算术题很残酷：

| 音频 | 句子数 | 分块数 | 串行（按 220s/块） | 并发 4 |
|---|---|---|---|---|
| 5.5 分钟 | 71 | 6（跳过 4 块后 2 块） | 约 7 分钟 | 约 4 分钟 |
| **20 分钟** | **259** | **约 17** | **约 30~60 分钟** | 约 8~15 分钟 |

（首次探针 220 秒；紧接着在同一实例上再打一次，**7 分钟仍未返回** ——
模型服务延迟的方差本身就很大，这也解释了为什么"有时候几分钟、有时候像卡死"。）

**顺带排除掉一个容易走错方向的猜测**：prompt 体积不是瓶颈。整块 4211 字符
（其中 JSON Schema 占 1331），换算约 2000 token，对百万级上下文可忽略；
而且这次 `promptTokens=2032` 与估算吻合。**所以压缩 schema / 精简 prompt 都救不了这个问题。**

**修法：把"串行 17 次"改成"并发若干次"。**

各分块之间是**天然独立**的 —— 每块只读自己那段文字、只产出自己那几条问答对，
彼此不共享任何状态。所以并发是这里唯一有效、且不牺牲质量的手段：

| 改动 | 位置 |
|---|---|
| 分块抽取改为并发（`CompletableFuture` + 独立线程池，队列 256、`CallerRunsPolicy` 兜底） | `InterviewQaExtractor.extract(..., concurrency)` |
| 并发度可配，默认 4（与 `interviewExecutor` 的 corePoolSize 一致，避免把模型服务打爆） | `interview.report.extraction-concurrency` |
| **按块预置结果槽位、最后按块序合并**，保证问答对仍按对话时间排列（并发不改变输出顺序） | 同上 |
| 单块异常仍然只记 `failedChunks` 并继续（失败隔离在并发下同样成立） | 同上 |
| 每次 LLM 调用打印**耗时 + prompt/completion token + finishReason** | `LlmJsonSupport` |
| 抽取调用加上固定 `seed=42`，与低温一起保证"同输入同输出"（AC-13） | `LlmJsonSupport` |

预期效果（按实测 220 秒/块、并发 4 保守估算）：

| 音频 | 待抽取块 | 串行 | 并发 4 |
|---|---|---|---|
| 5.5 分钟 | 2 | 约 7 分钟 | 约 4 分钟 |
| 20 分钟 | 约 17 | **30~60 分钟** | **约 15~20 分钟**（5 批 × 220 秒 + 转写） |

也就是说并发把耗时**按批数**压下来，但**不会让单次调用变快** ——
如果模型侧延迟是 220 秒量级，20 分钟音频的分析仍然要十几分钟。
要再往下压只有两条路，都不在本次改动范围内：
① 降低单次调用的输出量（例如不要让模型输出 topics / answerQuotes 这类"可后处理"的字段）；
② 换成非推理模型做抽取（当前模型 completion 的 8000 token 里绝大部分是"思考"）。

**需要观察的风险**：并发调高可能触发模型侧限流，表现是日志里
`分块抽取失败，已跳过该块继续: chunk=x/17`（此时该块的问答对会缺失，
报告头部会标出"失败块"）。真遇到就执行 `interview.report.extraction-concurrency: 3`（或 2）。
`spawn`/限流的具体阈值无法从客户端预判，只能按实际日志调。

### 9.9 追问：能不能用参数关掉"思考"？——能，但省不干净

> 用户追问："模型是不是可以设置参数关闭思考推理"。

先说通道：Spring AI 的 `OpenAiChatOptions` 有 **`extraBody(Map)`**，可以把任意厂商扩展字段
塞进请求体（`OpenAiApi.ChatCompletionRequest` 里确实有 `extraBody()` 字段）；
另外它还有一个 `reasoningEffort()`。所以**不需要改框架就能试**。

同一条 prompt（50 句 / 8 轮）A/B 实测（每档带硬超时，避免服务端 400 被 Spring AI 默认
10 次重试拖死）：

| 配置 | 耗时 | completionTokens | 结论 |
|---|---|---|---|
| A 基线（只设 `temperature=0.1`） | **&gt;150s 超时** | — | 与 §9.8 的 220s 同一量级 |
| B **`enable_thinking: false`** | **120.0s** | **5075** | ✅ 被服务端接受，completion 省 37% |
| C `thinking_budget: 0` | 142.0s | 5584 | ✅ 也被接受，但不如 B |

**所以能关，而且已经配置进去了**（`interview.report.extra-body` + `extra-body-keys`）。
但必须说清两件事，避免误判：

1. **"关思考"没有把 completion 降到输出量级**：B 档 5075 token 对应的 JSON 只有 3315 字符
   （约 1500 token），**剩下 3500 token 仍在"想"**。这个模型大概是混合推理，
   `enable_thinking` 只削掉了一部分，不是开关式的彻底关闭。
2. **不能靠加大分块来进一步减少调用次数**：把块从 8 轮加到 16 轮（56 句）后，
   completion **9445 token**，已经贴住 `maxTokens: 10000` 的天花板；
   再加到 40 轮（140 句）**220 秒仍未返回**（超时）。
   也就是说**块再大就会因截断而变成"分块抽取失败"**，反而丢问答对。

**结论**：关思考 + 并发 4 + 块大小维持 8，是当前证据下最稳的组合。
想再快只有一个方向 —— 换模型（`interview.report.extraction-model` 已经预留），
用一个非推理模型做抽取，因为抽取不需要对话模型那种表达能力。

> **测量方法上的两个坑（记录备查）**：① 探针的耗时打印依赖 `submit()` 是否立即返回，
> 某些情况下会打出 1ms 这种无效值 —— **只有 `completionTokens` 是可信的**；
> ② 一定要给探针加硬超时并关掉 Spring AI 的重试模板，否则一个 400 会重试 10 次、
> 把探针挂到看不出结果。

## 10. 2026-10 重构：问答清单改为"直接格式化"，分块抽取整条链路删除

> 起因（用户原话）："最终的问答清单不需要这么复杂了，不需要分块了，
> 直接将转换出来的文字列表格式化一下就成了问答清单就行。"
>
> 本文 §1~§9 保留为**历史记录**：那套分块并发抽取已经**不在代码里了**
> （`InterviewQaExtractor` 已删除）。当前实现见本节。

### 10.1 改成了什么

```
旧：
  句子列表 → buildTurns 切轮次 → partition 每 8 轮一块 → 逐块并发调 LLM（单块实测最长 220s）
           → 合并 → 去重 → 重新编号 → QaPair（question + answerSummary + answerQuotes + topics）

新：
  句子列表 → mergeBySpeaker 合并同人连续发言 → 按轮次成对（面试官块=Q，候选人块=A）
           → 全局编号 → QaItem（question + answer，两侧都是逐字原文）
```

| 项 | 旧 | 新 |
|---|---|---|
| 问答清单的生成方式 | 分块 + 每块一次 LLM | **纯内存格式化，零 LLM** |
| 40 分钟音频的耗时 | 十几分钟（并发 4） | **毫秒级** |
| token | 约 175k 输入 + 大量"思考"输出 | **0** |
| 时间戳来源 | 模型输出句子序号 → 系统查表回填 | 直接取问答两侧真实句子的 `begin_ms`/`end_ms`（误差恒为 0） |
| 失败模式 | 单块截断/限流 ⇒ `failedChunks` | 不存在（没有外部调用） |
| 配对范围 | 只有"真提问"被抽出（漏则不可见） | **全量成对**（岗位介绍、改约也会成条，不漏内容） |
| 全流程 LLM 调用 | 1（角色）+ N（分块）+ 1（报告） | **2**（角色 + 知识点归纳） |

### 10.2 配对口径（这是本次唯一需要"决策"的地方）

```
面试官发言块 → 候选人发言块   = 一条问答
面试官发言块 → 面试官发言块   = 并入同一个问题
候选人先开口（开场）          = 独立条目，Q 填"（开场发言）"
结尾面试官说完、候选人没回     = 保留条目，A 填"（未作答）"
```

**为什么不做"这是不是真提问"的判断**：`interView.m4a` 的 76 句里只有 2 句是提问，
如果要筛，就只有写规则（转写稿常丢标点 ⇒ 必漏）或调模型（正是本次要拆的东西）两条路。
所以选**全量成对**：清单会长一些、会混入非技术条目，但**一条不漏、结果可复现**，
需要核对时看报告第四部分的逐句原文。

代价要认下来：这段音频按新口径会产出 **20 条**问答条目，而"真提问"只有 2 条。
这是刻意的取舍，不是 bug。若日后确实要标注"哪条是真提问"，建议做成**打标而非过滤**
（在 `QaListBuilder` 里加一个布尔字段 `questionLike`），避免又把内容丢掉。
